# WeCraft 设计训练协作平台 · 详细使用说明

> 文档版本：MVP v1.0  
> 更新日期：2026-11-12  
> 适用对象：项目负责人、设计负责人、内容负责人、编辑、标注/QA、AI 工程、平台管理员、只读观察者  
> 文档定位：内部演示、试点验收与日常操作手册

---

## 1. 平台是什么

WeCraft 设计训练协作平台是一个独立的内部 Web 应用，用来管理设计 brief、优质案例、反例、候选设计、双评、盲测、实验记录、训练数据集和审计证据。

它解决的是“设计训练数据如何被生产、评审、授权和导出”的问题，不是模型训练平台。

### 1.1 平台负责

| 能力 | 说明 |
| --- | --- |
| Brief 管理 | 版本化保存正文、图片、读者、设计委托、品牌要求和禁止项 |
| 案例入库 | 管理优质案例与反例，保存截图、HTML、机制标签、六维评分和授权台账 |
| 独立评审 | 两人独立评分，分歧进入裁决，提交后不可原地修改 |
| 候选与硬检查 | 接收 AI 候选稿，执行正文、图片、安全 HTML、375px 溢出和对比度检查 |
| 盲测 | A/B 匿名比较，隐藏模型、来源和上一轮分数，双评后裁决 |
| 数据准备 | 查看覆盖率、授权完整度、评审一致性、硬失败率和盲测结果 |
| 数据集导出 | 校验训练或评测授权，冻结版本，导出 JSONL/CSV/ZIP，并记录审计 |

### 1.2 平台不负责

- 不替代飞书文档、沟通和项目排期。
- 不在平台内运行模型训练或微调。
- 不直接修改 WeCraft 生产代码，也不连接生产数据库。
- 不自动生成最终设计稿；候选稿由 AI 工程上传或通过接口写入。
- MVP 不自动发送邮件，不发送真实飞书消息。

### 1.3 三类对象不要混用

| 对象 | 用途 | 是否代表“好设计” |
| --- | --- | --- |
| 优质案例 Case | 可复用、可提炼机制、可进入训练或评测的数据 | 是，但仍需授权和双评 |
| 反例 Counterexample | 记录失败方式、根因和修复建议 | 否，是负向样例 |
| 候选 Candidate | AI 生成、等待硬检查和盲测的设计稿 | 未知，必须先验证 |

## 2. 如何进入平台

### 2.1 访问地址

当前本机演示地址：

`http://127.0.0.1:3001`

注意：`3000` 端口可能被 WeCraft 生产开发服务占用，因此训练平台默认使用 `3001`。

Workspace ID：

### 2.3 多角色演示方式

评审流程至少需要两个不同账号。推荐：

1. 普通 Chrome 窗口登录 `annotator@example.test`。
2. 无痕窗口登录 `lead@example.test`。
3. 另一个无痕窗口登录 `owner@example.test`。
4. 不要在同一浏览器普通标签页反复切换账号，否则会共用同一个 `dt_session` Cookie。

### 2.4 启动与重置

首次启动或服务停止后：

```powershell
cd G:\染殇泪\公司\wecraft-design-training-platform
npm run start -- -p 3001
```

开发模式：

```powershell
npm run dev -- -p 3001
```

恢复演示数据：

```powershell
npm run db:seed
```

`db:seed` 会清空并重建演示 Workspace，仅用于开发和演示。E2E 测试也会写入额外数据，演示前应重新播种。

## 5. 流程 A：Brief 与案例入库

目标：从内容需求开始，形成一张通过双评、授权完整、可进入数据集的优质案例。

### 5.1 创建 Brief

使用 `content@example.test` 或 `editor@example.test` 登录，进入 `/briefs`。

点击“新建 Brief”，填写：

| 字段 | 填写要求 |
| --- | --- |
| 标题 | 可识别的内容主题，不要只写“测试 1” |
| 用途 | 案例来源、黄金评测、案例 + 评测 |
| 数据集拆分 | DEV 研发集或 HOLDOUT 保留集 |
| 目标读者 | 明确读者画像和阅读场景 |
| 正文 Markdown | 真实正文或经过脱敏的完整样例 |
| 设计委托 | 对版式、视觉机制、材料、节奏的明确要求 |
| 品牌要求 | 颜色、字体、语气、品牌资产限制 |
| 禁止项 | 明确不能出现的内容、形式或表达 |

保存后：

- Brief 自动生成版本。
- 后续修改会创建新版本，不覆盖旧版本。
- Holdout Brief 只有 `OWNER` / `ADMIN` 可见。
- 普通评审任务不会包含 Holdout Brief。

### 5.2 创建案例

使用 `annotator@example.test` 或 `lead@example.test` 登录，进入 `/cases/new`。

页面采用“左侧截图、右侧结构化字段”布局。

#### 必备资产

1. 375px 截图：支持 PNG、JPEG、WebP、SVG；也接受 750px 的 2x 截图。
2. HTML 证据：平台会清洗后放入 `sandbox=""` iframe。

截图要求：

- 能看清真实移动端版式，不要用桌面宽图裁剪冒充。
- 文件建议小于 8 MB。
- 截图中的文字、图片位置和 HTML 预览应一致。

HTML 要求：

- 不使用脚本、表单、iframe、外链资源和 `javascript:`。
- 外部图片请转换成 data URL，或改用截图作为证据。
- 预览区不允许外部网络请求。

#### 案例卡字段

| 字段 | 说明 |
| --- | --- |
| 案例标题 | 用一句可识别的话描述案例 |
| 主型 | 自我指涉、材料语言、场景叙事、类型借用、图式结构、界面语言、引用与拼贴、心理感知、过程留痕 |
| 来源 Brief | 关联内容需求，允许“不关联” |
| 适用内容条件 | 什么内容适合用；什么内容不适合用 |
| 设计机制 | 设计如何与内容结构发生关系，避免只写“好看”“高级” |
| 机制标签 | 用逗号分隔，便于后续检索和聚类 |
| 来源类型 | 内部原创、用户内容、第三方、公共领域 |
| 反模式 | 每行一条，描述该机制容易产生的失败 |
| 来源说明 | 说明素材来源、授权背景和脱敏情况 |
| 六维自评 | 1–5 分；图像叙事允许 N/A |

#### 六维评分

| 维度 | 代码 | 判断重点 |
| --- | --- | --- |
| 内容适配 | `CONTENT_FIT` | 设计是否回应正文、读者和传播目标 |
| 视觉机制 | `VISUAL_MECHANISM` | 是否有清晰、可复用的设计机制 |
| 字形层级 | `TYPE_HIERARCHY` | 标题、导语、正文层级是否清楚 |
| 图像叙事 | `IMAGE_NARRATIVE` | 图片是否承担叙事，而非纯装饰；无图可 N/A |
| 节奏变化 | `RHYTHM` | 留白、密度、段落转换是否有呼吸 |
| 整体完成度 | `COMPLETION` | 交付完成度、细节和一致性 |

保存案例后，进入案例详情。

### 5.3 填写授权

使用 `owner@example.test` 或 `lead@example.test` 登录，进入案例详情。

六项授权默认全部为 `false`：

| 授权 | 含义 | 典型用途 |
| --- | --- | --- |
| 可生成 `canUseForGeneration` | 可作为生成参考 | 提示词、检索、风格参考 |
| 可展示 `canUseForDisplay` | 可在内部或产品中展示 | 案例库、演示、评审 |
| 可训练 `canUseForTraining` | 可进入训练数据 | 训练集导出 |
| 可提炼机制 `canDeriveMechanism` | 可抽取设计规则和机制 | 设计知识库 |
| 可评测 `canUseForEvaluation` | 可进入评测数据 | 评测集导出 |
| 可公开展示 `canShowPublicly` | 可对外公开 | 官网、公众号、对外材料 |

操作建议：

1. 逐项确认原始授权证据。
2. 选择证据状态 `MISSING`、`PARTIAL`、`VERIFIED` 等。
3. 填写证据说明，例如合同条款、授权邮件、来源备注。
4. 填写本次修改理由，写入审计。
5. 保存授权。

规则：

- 只有 `OWNER` 和 `DESIGN_LEAD` 可以修改授权。
- `ADMIN` 可以管理平台和导出，但不能代替设计负责人修改训练授权。
- 训练集导出至少需要 `canUseForTraining=true`。
- 评测集导出至少需要 `canUseForEvaluation=true`。

### 5.4 提交案例并分配评审

1. 在案例详情确认截图和 HTML 资产已存在。
2. 点击提交案例。
3. 由 `OWNER`、`DESIGN_LEAD` 或 `CONTENT_LEAD` 分配至少两名评审。
4. 评审人应是不同账号，且不能是案例作者。
5. 评审人登录后进入 `/inbox`。

### 5.5 独立评审

评审人打开 `/tasks/:id`，检查：

- 375px 截图。
- 沙箱 HTML 预览。
- Brief 内容和设计委托。
- 设计机制和适用条件。
- 版本信息。

提交内容：

- 可发布结论。
- 总体理由。
- 六维评分。
- 至少一条证据：截图区域、HTML 片段或正文摘录。
- 定位和证据说明。

规则：

- 两名评审全部提交前，看不到对方分数。
- 提交后不能原地修改。
- 需要修改时点击“创建评审修订”，填写修订理由，生成新版本。
- 旧评审被标记为 `SUPERSEDED`，新版本和审计记录保留。

### 5.6 分歧与裁决

两名评审结论不一致时，案例进入 `ARBITRATION`。

裁决人使用 `lead@example.test` 或 `owner@example.test`：

1. 进入 `/inbox` 或案例详情。
2. 查看双方评分、理由和证据。
3. 选择结果：
   - `ELIGIBLE`：进入可入库状态。
   - `CHANGES_REQUESTED`：退回修改。
   - `REJECTED`：拒绝。
4. 填写裁决理由。
5. 提交裁决。

案例进入 `ELIGIBLE` 后，才具备进入训练集或评测集的前置资格；授权不完整仍会阻止数据集导出。

### 5.7 常见状态

| 状态 | 含义 |
| --- | --- |
| `DRAFT` | 草稿 |
| `SUBMITTED` | 已提交 |
| `IN_REVIEW` | 评审中 |
| `ARBITRATION` | 有分歧，等待裁决 |
| `CHANGES_REQUESTED` | 退回修改 |
| `ELIGIBLE` | 已具备入库资格 |
| `REJECTED` | 已拒绝 |
| `ARCHIVED` | 已归档 |

## 6. 流程 B：候选设计、硬检查与盲测

目标：把 AI 候选稿匿名比较，形成可追溯的偏好记录和实验结论。

### 6.1 提交候选

使用 `engineer@example.test` 登录，进入 `/candidates/new`。

填写：

| 字段 | 说明 |
| --- | --- |
| 标题 | 候选稿名称 |
| Brief | 必须选择本次实验对应的 Brief |
| 模型供应商 | 例如内部模型、第三方模型名称 |
| 模型名称 | 具体模型 |
| 模型版本 | 版本号或日期快照 |
| HTML | 候选设计 HTML |
| 375px 截图 | 移动端视觉证据 |

提交后候选处于 `SUBMITTED`。模型、版本等元数据只对实验管理角色可见，盲测评审不能看到。

### 6.2 运行五项硬检查

进入候选详情，点击“运行硬检查”。

| 规则 | 检查内容 | 严重级别 |
| --- | --- | --- |
| HC-01 | 正文完整性：正文长度、占位内容 | BLOCK |
| HC-02 | 图片位置：fixed 定位、alt 缺失 | WARN |
| HC-03 | 安全 HTML：脚本、事件、表单、外链、meta refresh | BLOCK |
| HC-04 | 375px 横向溢出 | BLOCK |
| HC-05 | 正文对比度是否达到 4.5:1 | BLOCK |

结果：

- 无 BLOCK 失败：候选进入 `READY_FOR_BLIND`。
- 存在 BLOCK 失败：候选进入 `HARD_CHECK_FAILED`。
- 浏览器渲染器不可用：HC-04/HC-05 fail-closed，候选不能进入盲测。

如果 HC-04/HC-05 返回 ERROR：

1. 确认本机安装了 Chrome/Chromium。
2. 检查 `.env` 的 `PLAYWRIGHT_CHROMIUM_EXECUTABLE`。
3. 或执行 `npx playwright install chromium`。
4. 重新运行硬检查。

### 6.3 创建盲测实验

使用 `engineer@example.test`、`lead@example.test` 或 `owner@example.test` 进入 `/experiments/new`。

选择：

- 实验名称。
- 非 Holdout Brief。
- 同一 Brief 下两个 `READY_FOR_BLIND` 候选。
- 评审 A。
- 评审 B。
- 裁决人。

如果候选不足两个，先回到候选详情运行硬检查。

### 6.4 进入盲测房间

评审人使用自己的账号进入 `/experiments/:id/blind`。

房间规则：

- 只显示方案 A / 方案 B。
- 隐藏模型供应商、模型名称、模型版本、候选编号、案例来源和上一轮分数。
- 可切换查看 A/B 的 375px 截图。
- HTML 只在沙箱 iframe 中预览。

操作顺序：

1. 阅读 Brief、设计委托和禁止项。
2. 查看方案 A 的截图和 HTML。
3. 查看方案 B 的截图和 HTML。
4. 核对双方硬检查结果。
5. 勾选“我已独立核对双方硬检查结果”。
6. 分别完成 A/B 六维评分。
7. 选择更优方案：方案 A、方案 B 或平票。
8. 填写判断理由和置信度。
9. 提交。

提交后：

- 页面显示“已提交”。
- 分数和偏好不能原地修改。
- 两名评审全部提交前，互相看不到分数。

### 6.5 盲测裁决与实验关闭

两名评审提交后，系统生成待裁决状态。

裁决人：

1. 打开 `/inbox`。
2. 进入对应盲测裁决任务。
3. 查看双方评分、偏好和理由。
4. 选择最终偏好：方案 A、方案 B 或平票。
5. 填写裁决理由。
6. 提交，Pair 状态变为 `COMPLETED`。

实验结束后，由 `OWNER`、`ADMIN`、`DESIGN_LEAD` 或 `AI_ENGINEER` 在实验详情点击“关闭实验”。

只有实验关闭后，管理角色才能读取完整比较记录。TIE 保留在统计中，但不进入偏好训练数据。

### 6.6 常见状态

| 状态 | 含义 |
| --- | --- |
| `SUBMITTED` | 候选已提交 |
| `HARD_CHECKING` | 硬检查中 |
| `HARD_CHECK_FAILED` | 存在 BLOCK 失败 |
| `READY_FOR_BLIND` | 已通过硬检查，可进入盲测 |
| `IN_BLIND` | 已进入盲测 |
| `COMPLETED` | 比较或实验已完成 |
| `WITHDRAWN` | 已撤回 |
| `DISQUALIFIED` | 已取消资格 |

## 7. 流程 C：数据集校验与导出

目标：把通过评审且授权完整的数据冻结成可追溯版本，并导出为训练或评测数据。

### 7.1 创建数据集

使用 `owner@example.test`、`lead@example.test` 或 `engineer@example.test` 进入 `/datasets/new`。

填写：

- 数据集名称。
- 类型：训练集 TRAIN 或评测集 EVAL。
- 勾选优质案例。
- 勾选 Brief。
- 勾选反例。
- 勾选候选设计。

选择原则：

- 训练集只导出 `canUseForTraining=true` 的对象。
- 评测集只导出 `canUseForEvaluation=true` 的对象。
- Holdout 不得进入训练集。
- 不要把未评审、未批准或授权不明的对象混入训练集。

### 7.2 执行校验

进入数据集详情，点击“执行校验”。

平台会检查：

- 对象是否存在且已具备资格。
- 案例是否完成双评。
- 授权字段是否满足训练或评测要求。
- 是否误用 Holdout。
- 版本和授权是否发生漂移。
- 是否存在法律冻结或其它阻断。

校验结果：

- 无阻断：进入 `READY_FOR_APPROVAL`。
- 有阻断：进入 `BLOCKED`，页面显示具体条目和原因。

### 7.3 修复阻断

常见阻断和修复方式：

| 阻断 | 修复方式 |
| --- | --- |
| `RIGHTS_MISSING` | 由 Owner/Design Lead 补齐并核验训练或评测授权 |
| `NOT_ELIGIBLE` | 完成案例双评和裁决，使案例进入 ELIGIBLE |
| `REVIEW_INCOMPLETE` | 分配并完成两名独立评审 |
| `HOLDOUT_IN_TRAIN` | 从训练集移除 Holdout 对象 |
| `VERSION_DRIFT` | 重新校验，接受新版本或回退到冻结版本 |
| `LEGAL_HOLD` | 联系 Owner/管理员处理法律冻结，不得绕过 |

修复后重新点击“执行校验”，直到没有阻断。

### 7.4 批准与冻结

由 `OWNER` 或 `DESIGN_LEAD` 点击“批准数据集”。

批准会：

- 冻结每个条目的案例/反例/Brief/候选版本。
- 冻结授权快照。
- 生成 manifest hash。
- 记录批准人和批准时间。

冻结后不允许静默替换条目。需要变更时必须创建新数据集版本。

### 7.5 导出

由 `OWNER`、`ADMIN` 或 `DESIGN_LEAD` 点击“导出 JSONL / CSV ZIP”。

导出包包括：

- JSONL 数据。
- CSV 汇总。
- manifest。
- 必要的截图/HTML 资产。

导出后：

- 页面显示临时下载链接。
- 下载链接 15 分钟内有效。
- 导出动作写入审计，记录导出人、时间、版本、hash 和文件大小。
- 下载动作还会单独写入审计。

### 7.6 常见状态

| 状态 | 含义 |
| --- | --- |
| `DRAFT` | 草稿，尚未校验 |
| `VALIDATING` | 校验中 |
| `BLOCKED` | 存在阻断，不能批准/导出 |
| `READY_FOR_APPROVAL` | 校验通过，等待批准 |
| `APPROVED` | 已批准并冻结 |
| `READY` | 已准备完成 |
| `EXPORTING` | 导出中 |
| `FAILED` | 导出或校验失败 |

## 8. 仪表盘怎么看

进入 `/dashboard`。

| 指标 | 口径 | 用法 |
| --- | --- | --- |
| 优质案例 | 已具备资格的案例数 / 30 | 判断案例生产是否接近目标 |
| 授权完整度 | 证据已核验的已批准案例 / 已批准案例 | 发现不能合法进入训练的数据 |
| 评审完成度 | 已完成双评的案例 / 案例总数 | 发现评审积压 |
| 硬失败率 | 最新硬检查存在 BLOCK 的候选 / 已检查候选 | 判断 AI 输出质量和渲染稳定性 |
| 主型覆盖 | 9 个主型分别有多少已批准案例 | 找设计类型缺口 |
| 评审一致性 | 可发布结论一致率 + 各维平均绝对差 | 发现评分口径漂移 |
| 盲测比较数 | 已提交的 A/B 比较数量 | 判断偏好样本量 |
| 偏好明确率 | 非 TIE 比较 / 全部比较 | 判断候选差异是否足够明显 |
| TIE 比例 | 平票 / 全部比较 | 判断评审是否难以区分候选 |
| 候选胜率 | 候选在已完成比较中的胜出比例 | 辅助判断模型或版本表现 |
| 数据准备度 | 案例、反例、黄金 Brief 当前值 / 目标值 | 判断是否具备训练/评测规模 |

重要：数据准备度不是完成率。未解决分歧、授权缺失、BLOCK 硬检查和 Holdout 误用都会阻止导出。

## 10. 审计与安全

### 10.1 审计日志

进入 `/settings/audit`。

会记录：

- 登录。
- 邀请和成员角色变更。
- 授权变更。
- 案例提交、评审提交和裁决。
- 案例发布或状态变更。
- 数据集校验、批准、导出和下载。

每条记录包含操作人、动作、资源、理由、时间、请求元数据、`prevHash` 和 `entryHash`。

审计日志是追加式哈希链，可用于发现断链或单条篡改。

### 10.2 HTML 预览安全

- HTML 只在 `sandbox=""` iframe 中显示。
- 不授予脚本执行权限。
- 响应包含 CSP，禁止脚本、表单、外链资源和网络请求。
- 外部 URL 会被清洗。
- 内联样式保留用于视觉还原，但只能在沙箱内影响预览区域。

### 10.3 数据隔离

- 每个查询都带 Workspace 条件。
- 跨 Workspace 资源统一返回 404。
- Holdout 在列表、详情、任务、数据集和文件读取层分别过滤。
- 数据集 ZIP 不能通过通用文件接口直接读取，只能走带审计的下载接口。

### 10.4 导出安全

- 只有 `OWNER`、`ADMIN`、`DESIGN_LEAD` 可以导出数据集。
- 导出前再次检查授权和版本快照。
- 授权缺失、版本漂移或 Holdout 误用会阻断导出。
- 导出和下载均写审计。

## 12. 常见问题

### Q1：为什么访问 3000 打不开训练平台？

3000 可能被 WeCraft 生产开发服务占用。训练平台使用：

`http://127.0.0.1:3001`

### Q2：为什么看不到 Holdout Brief？

Holdout 只允许 `OWNER` / `ADMIN` 查看。普通角色看到 404 或列表为空是预期行为。

### Q3：为什么不能修改训练授权？

训练授权只允许 `OWNER` 或 `DESIGN_LEAD` 修改。`ADMIN` 也不能修改训练授权。

### Q4：为什么评审提交后不能改分数？

这是审计要求。点击“创建评审修订”，填写修订理由后生成新版本，旧版本保留为 `SUPERSEDED`。

### Q5：为什么两名评审互相看不到分数？

盲测和独立评审在双人提交前隐藏对方结果，避免锚定。双评完成后再进入裁决。

### Q6：为什么数据集被 BLOCKED？

展开阻断项查看具体原因。最常见的是：

- 缺少 `canUseForTraining`。
- 案例尚未进入 `ELIGIBLE`。
- 双评未完成。
- Holdout 被加入训练集。
- 版本或授权发生变化。

### Q7：硬检查为什么返回 ERROR？

通常是 Chrome/Chromium 渲染器不可用。检查：

```dotenv
PLAYWRIGHT_CHROMIUM_EXECUTABLE="C:/Program Files/Google/Chrome/Application/chrome.exe"
```

或执行：

```powershell
npx playwright install chromium
```

然后重新运行硬检查。

### Q8：HTML 预览为什么有内容缺失？

平台会移除脚本、表单、iframe、外链图片和外部 CSS。请把必要图片转换为 data URL，或使用截图作为证据。

### Q9：截图上传失败怎么办？

确认：

- 宽度为 375px 或 750px（2x）。
- 格式为 PNG、JPEG、WebP 或 SVG。
- 文件小于 8 MB。
- 不是桌面宽图。

### Q10：演示数据乱了怎么办？

执行：

```powershell
npm run db:seed
```

然后重新登录。所有演示账号密码恢复为 `Demo1234!`。

## 13. 当前限制

MVP 已经可演示和验收，但以下能力尚未完成生产化：

- 飞书 OAuth 和真实飞书消息未接入；当前为邮箱登录和站内通知。
- 邮件邀请不会自动发送，只生成一次性链接。
- 对象存储当前为本地文件系统，S3/OSS 适配尚未接入。
- 硬检查在 Web 进程内同步运行，尚无独立队列和隔离 runner。
- 截图需要人工上传，没有自动服务端截图生成。
- 批量分配和保存视图尚未实现，待办仅有类型筛选。
- 备份恢复、监控告警和真实生产环境压测尚未执行。
- Docker Compose 尚未在干净 Linux 环境实测。
- 当前依赖审计仍有 6 个 moderate、7 个 high、0 个 critical，主要修复需要大版本升级。

正式上线前，必须以 `docs/known-limitations.md` 和 `docs/test-report.md` 为基线完成关闭或书面风险接受。

## 15. 一句话总结

先用 Brief 定义内容，再用案例卡和双评沉淀可复用设计；候选稿必须经过硬检查和匿名盲测；进入训练或评测前，必须完成授权校验、版本冻结和可追溯导出。
