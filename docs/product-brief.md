# WeCraft 设计训练协作平台：任务基线

> 本文件是新仓库的唯一任务基线。产品文档、契约、代码和测试均在本仓库维护，不写入 WeCraft 生产仓库。

## 1. 背景与边界

WeCraft 是公众号内容创作与设计平台。团队需要在同一平台中协作完成设计案例采集、案例标注、设计评审、盲测、实验记录和训练数据准备。

这里的“训练”指为提升 AI 设计能力准备案例、偏好数据和评测集，不在平台内运行模型训练，也不是员工培训。

平台是独立部署的内部 Web 应用：

- 平台负责：Brief、优质案例、反例、候选设计、评审、盲测、授权台账、硬检查、数据集导出、通知和审计。
- WeCraft 生产系统负责：设计生成、案例检索、提示词组装、渲染和线上审稿闭环。
- 两条系统通过版本化契约集成，不共享源码、数据库、对象存储、环境变量或飞书应用。
- MVP 为模块化单体，不拆微服务；不做双向实时同步。

现有训练方案参考：<https://acnw98kbqn7h.feishu.cn/wiki/Nh06wlqroi7i9mkSvE7cLBRYnyv>

## 2. 目标

- 4–20 人的团队可在桌面端完成 brief 管理、案例/反例入库、独立评分、裁决、候选硬检查与盲测、实验记录、数据集导出和运营指标查看。
- 当前约 12 个设计案例，目标扩展到 30–40 个优质案例和 10–20 个反例；黄金评测集为 60–100 个 brief。
- 优质案例、反例、候选设计是不同对象，不混表；案例与 Brief 版本化；评审不可静默修改。
- 非技术设计师和编辑能独立完成案例录入与评审；盲测隐藏模型版本、案例来源和上一轮分数。

## 3. 角色

- 项目负责人 `OWNER`
- 平台管理员 `ADMIN`
- 设计负责人 `DESIGN_LEAD`
- 内容负责人 `CONTENT_LEAD`
- 内容/编辑 `EDITOR`
- 标注/QA `ANNOTATOR`
- AI 工程 `AI_ENGINEER`
- 只读观察者 `VIEWER`

权限采用 Workspace 级 RBAC + 资源级校验，服务端鉴权；作者不得评审自己的案例，候选提交人不得评审自己的候选；跨 Workspace 统一返回 404。

## 4. 核心工作流

1. 内容/编辑创建 brief，填写正文、图片、目标读者、设计委托、品牌要求和禁止项。
2. 设计师/标注人员创建案例卡，填写授权、适用内容条件、设计机制、截图、HTML、六维评分和反模式。
3. 第二名评审独立评分，分歧进入裁决。
4. AI 工程提交候选设计，平台执行硬检查并进入盲测。
5. 评审在盲测房间中比较 A/B 方案，提交六维评分和偏好选择。
6. 项目负责人查看覆盖率、评审一致性、硬失败率、盲测胜率和数据准备度。
7. 负责人将符合授权的案例导出为训练或评测数据集。

### 必须端到端可用

**流程 A：案例入库**
创建 brief → 创建案例 → 上传截图和 HTML → 第一名评审填写案例卡 → 第二名评审独立评分 → 分歧裁决 → 案例进入 `ELIGIBLE`。

**流程 B：盲测评审**
创建盲测任务 → 随机展示 A/B → 两名评审独立提交硬检查和六维评分 → 系统计算分歧 → 裁决人确认 → 结果进入实验记录。

**流程 C：数据集导出**
创建数据集 → 系统检查所有条目的训练授权 → 有缺失则阻止导出 → 无缺失则生成版本快照 → 导出 JSONL/CSV → 写入审计日志。

## 5. MVP P0 范围

1. 登录、用户邀请、角色与权限。
2. Brief 列表、详情、创建、编辑、版本和 dev/holdout 标记。
3. 案例库：优质案例/反例、案例卡、截图、HTML、授权、机制标签、六维评分。
4. 案例标注任务：分配、待办、提交、独立评分、分歧裁决。
5. 候选设计：上传或 API 写入 HTML/截图，记录模型、版本和实验信息。
6. 硬检查：正文完整性、图片位置、安全 HTML、375px 溢出、对比度。
7. 盲测房间：A/B 随机展示，隐藏模型和来源，提交评分与偏好。
8. 仪表盘：主型覆盖、授权完整度、评审完成度、评审一致性、硬失败率、盲测胜率、数据准备度。
9. 数据集：筛选、授权校验、版本快照、JSONL/CSV 导出。
10. 审计日志：登录、授权变更、评审提交、案例发布、数据导出。
11. 通知中心与飞书通知适配。
12. 软删除、恢复和法律冻结占位。

不做：模型训练/推理、真实飞书审批、移动端编辑、自动评分、自动裁决、Elo/Bradley–Terry、公开门户、修改 WeCraft 生产代码。

## 6. 数据模型最低要求

至少包含：`Workspace`、`User`、`Role`、`Membership`、`Invitation`、`Session`、`Brief`、`BriefVersion`、`Case`、`CaseVersion`、`CaseAsset`、`Counterexample`、`CounterexampleVersion`、`CounterexampleAsset`、`AuthorizationGrant`、`AuthorizationEvent`、`CaseReview`、`ReviewTask`、`ReviewScore`、`ReviewEvidence`、`Candidate`、`CandidateVersion`、`HardCheckRun`、`HardCheck`、`PairwiseComparison`、`PairwiseScore`、`Experiment`、`ExperimentPair`、`Dataset`、`DatasetItem`、`DatasetExport`、`AuditLog`、`Notification`。

关键规则：

- Brief 和 Case 必须版本化；版本内容不可 UPDATE。
- 优质案例与反例使用独立表、独立状态机，不能混用。
- 六项授权字段默认全部为 false：`canUseForGeneration`、`canUseForDisplay`、`canUseForTraining`、`canDeriveMechanism`、`canUseForEvaluation`、`canShowPublicly`；训练与评测授权不可互相推导。
- 只有 `OWNER` 或 `DESIGN_LEAD` 可修改训练/评测授权。
- 评审提交后不可原地修改；修改生成新版本并留审计记录。
- Dataset 导出必须锁定案例版本和授权快照。
- Holdout brief 不得出现在普通评审任务中，只有 `OWNER/ADMIN` 可见。
- 历史评分、模型版本、案例来源和他人分数在盲测提交前不可见。

## 7. 页面与交互

页面：登录、仪表盘、Brief 列表与详情、案例库与案例卡编辑器、标注任务队列、盲测评审房间、候选设计详情、实验列表与详情、数据集列表与导出页、成员/角色/权限设置、审计日志、通知中心。

- 中文界面，面向设计师、编辑和工程人员；桌面端优先，适配 1280px 以上。
- 案例卡采用“左侧截图、右侧结构化字段”的编辑布局。
- 长任务支持筛选、批量分配、保存视图。
- 所有状态有明确文字，不只靠颜色区分；空、加载、失败、权限不足均有清晰状态。
- 盲测房间支持 A/B 两侧切换 375px 截图；先硬检查，再六维评分；两名评审全部提交前互不可见分数；提交后显示“已提交”且不可直接修改；评分必须填写证据和理由。

## 8. 安全与数据治理

- 服务端鉴权，前端角色字段不可信。
- HTML 只在无脚本的 sandbox iframe 中预览，禁止表单、事件属性、脚本和外部网络请求。
- 截图生成和硬检查在服务端或隔离 runner 中执行。
- 数据集导出只允许 `OWNER/ADMIN/DESIGN_LEAD`；所有导出、授权修改和案例发布写审计。
- 用户内容不得跨 Workspace 读取。
- 密钥只来自 Secret Manager/环境变量，不入库、不进日志、不进前端。
- 数据库备份、对象存储生命周期和恢复演练写入部署文档。

## 9. 技术、交付与验收

默认技术建议：Next.js + Fastify/tRPC + PostgreSQL + Prisma + S3/OSS。允许替换，但必须在 ADR 中说明理由、迁移成本和运维方式。MVP 计划采用 Next.js App Router + Route Handlers 的模块化单体，业务服务层可抽取。

交付：可运行仓库、数据库 migration 和 seed、README/环境变量/部署说明、API 文档、E2E 或集成测试、演示账号和演示数据、已知限制与后续计划、测试报告和 demo 录屏或演示地址。

验收：三种角色完成各自工作流；案例标注和盲测完整走通；授权不完整时无法训练导出；评审提交不可覆盖；375px 截图可查看；恶意 HTML 无法执行脚本或请求外部资源；仪表盘指标正确；关键写操作有审计；关键流程有自动化测试；全新克隆可按 README 启动。

## 10. 工作方式

先检查仓库、文档和可复用能力；先冻结产品、数据、权限和验收，再实现。先完成端到端主流程，再做非关键优化；不擅自扩大范围。未确认的业务规则写成明确假设，不自行发明。
